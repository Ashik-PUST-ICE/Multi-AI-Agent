# Agent security threat model

This is the implementation threat model for the current release, mapped to the OWASP Agentic Top 10. It describes controls and residual risks; it is not a security certification or proof that model behavior is safe.

## Trust boundaries and assets

- **Untrusted inputs:** owner prompts, uploaded Knowledge, retrieved memory, web/MCP/REST responses, tool arguments, agent-pack guidance, and model output.
- **Sensitive assets:** owner and tenant data, encrypted provider/integration credentials, approved model selections, trust levels, and pending approvals.
- **Execution boundary:** authenticated `/api/v1` requests create owner-scoped tasks; workers claim pending runs under database locks; provider access is resolved by backend code for the run's owner and selected agent.
- **Tool boundary:** the application registers a fixed set of first-party tools. Agent specifications provide per-agent tool allowlists and trust floors. Sandbox calls only `simulate()`; Live calls require the relevant owner-controlled trust and approval checks.
- **Pack boundary:** only packs in the local database registry can be installed. Packs contain bounded agent guidance and examples, not executable scripts. Admin-authored definitions are signed with an HMAC derived from the application key.
- **External boundary:** configured providers and explicitly approved web, MCP, REST, and messaging integrations receive only the requests required for their operation. Responses remain untrusted.

## OWASP Agentic Top 10 mapping

| Risk | Exposure and current controls | Residual risk / release gate |
|---|---|---|
| ASI01 Agent Goal Hijack | The original task description is stored separately and its SHA-256 integrity is checked before work continues. Knowledge, memories, packs, and tool responses are treated as untrusted reference data. Skeptic checks the final answer against success criteria; unmet or uncertain criteria produce a `task.goal_drift_detected` event and a bounded retry. | Hash integrity detects storage tampering, not semantic drift. The Skeptic is a model-based check, not a proof; inspect drift events and do not treat approval as authorization. |
| ASI02 Tool Misuse | A fixed application registry rejects unknown tools. Each tool has an input schema and minimum trust level; agent specs cap which tools an agent can call. Live write/outbound calls require exact owner approval and are Never-Auto. Sandbox dispatches only `simulate()`. Per-task outbound reservations are serialized under a task lock and stop at the configured limit. | Tool descriptions are not a machine-verifiable description of implementation behavior. First-party code still needs review and adversarial tests. Live web search and outbound integrations are disabled unless an owner configures them and explicitly approves a call. |
| ASI03 Identity and Privilege Abuse | Tool execution context binds an agent-run identity to the matching owner, task, and tenant. Provider selection is restricted to that owner's approved models; encrypted credentials are scoped to both owner and agent, resolved only inside backend provider adapters, and never placed in prompts or handoff envelopes. Missing credentials fail closed without an owner-level fallback. Per-agent tool allowlists and trust levels limit capabilities. | Application-level separation does not restrict a key at the provider itself. Prefer provider-side scoped credentials when supported, rotate compromised keys, and treat any exposed key as compromised. |
| ASI04 Agentic Supply Chain | Tools are registered from application code; there is no endpoint for installing arbitrary tool code. Built-in and admin-authored local packs expose publisher identity and a SHA-256 definition fingerprint, authenticated with an application-key HMAC. External skills and executable packs are not installable. | HMAC verification depends on protecting and backing up the application key. There is no external publisher PKI/signature or automated semantic comparison of tool descriptions against code; external pack/skill installation must remain disabled. |
| ASI05 Unexpected Code Execution | Agent-directed code execution is not provided. The code tool routes only through the configured isolated sandbox service, is disabled by default, and cannot execute in Sandbox mode. Archive/file parsing uses bounded application integrations rather than model-supplied shell commands. | Parser and sandbox implementations remain attack surfaces; require container isolation and malicious-file regression tests before enabling code execution in production. Never add a host-shell fallback. |
| ASI06 Memory and Context Poisoning | User/task memory and Knowledge are owner-scoped and explicitly selected. Retrieved content and pack/skill guidance remain untrusted data; they cannot raise trust or add tools. Red-team tests cover hostile memory, file/reference text, and PII/credential-shaped log masking. | A model can still be influenced by poisoned reference data. Prompt-injection filtering is not a security boundary; maintain source provenance and review model outputs before sensitive actions. |
| ASI07 Insecure Inter-Agent Communication | Messages use a strict, versioned envelope. Workers verify task ID and recipient; handoff provenance must match the preceding completed agent. Atomic pending-to-running claims prevent duplicate queue deliveries from executing one run twice. | Envelopes are not cryptographically signed and do not contain a nonce. The current transport is internal database/queue only; do not expose it to external agents or accept owner-controlled raw envelopes without adding authenticated provenance and replay protection. |
| ASI08 Cascading Failures | Task, agent-run, and system kill switches stop work at provider/tool checkpoints. Duplicate run claims are rejected. Outbound calls are counted across all agents in the task; exceeding the limit halts the run and creates an owner-visible high-priority notification. | An in-flight provider or outbound HTTP request cannot be interrupted. Kill switches take effect at the next checkpoint; configure request timeouts and monitor halted-task notifications. |
| ASI09 Human-Agent Trust Exploitation | Access defaults to owner-controlled User mode. Approvals bind the exact normalized tool input; silence never authorizes a call. Never-Auto includes credentials, access changes, installation, destructive actions, locks/stoves/gas, payments, outbound messages, and security changes. Agents cannot create approvals or change access settings. | Human review remains vulnerable to confusing or incomplete UI. Show destination, payload, cost, and consequences before approval; never use agent-generated approval or success claims as consent. |
| ASI10 Rogue Agents | Agent specifications are versioned and schema-validated; active agent tool permissions cannot exceed their registered capabilities. Output is schema-checked with at most one correction attempt. Kill switches, trust ceilings, task budgets, and adversarial tests constrain rogue or compromised behavior. | Model output remains untrusted and may be persuasive or deceptive. Keep the four-agent core small, review spec changes, and use the independent Reviewer/Skeptic as defense-in-depth rather than as an authority. |

## Red-team and release checks

- Verify prompt injection in user prompts, Knowledge, memories, and tool responses cannot change trust, tool allowlists, or the stored task objective.
- Verify deceptive tool descriptions do not increase permissions, and unknown/unregistered tools cannot execute.
- Verify a handoff with a forged sender, wrong task, wrong recipient, unsupported schema version, or duplicate run claim is rejected.
- Verify Sandbox tool calls invoke only `simulate()`, including code, browser, messaging, REST, and MCP tools.
- Verify per-agent tool/trust restrictions, exact-input approval, system/task/agent kill switches, hard token/cost budgets, and task-wide outbound limits.
- Verify pack edits fail integrity checks if either the definition hash or signed metadata is altered.
- Keep external tool/pack/skill installation, host-shell execution, and unreviewed Live outbound actions disabled.
- Treat provider credentials as owner-scoped backend secrets. Do not copy them into prompts, memory, agent messages, tool arguments, activity logs, or replay data.
- Re-run migration, authorization, duplicate-job, objective-integrity, injection, malicious-file, and outbound-throttle tests when execution surfaces change.
